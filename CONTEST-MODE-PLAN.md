# План: строгий WPX/HST + верификация лога + лидерборд

Три задачи из ТЗ логически идут одна за другой: без движка верификации
(этап 1) нечего показывать в строгом режиме (этап 2), без строгого режима
нечего проверять на бэкенде (этап 3), без бэкенда нечего рисовать в
лидерборде (этап 4). План ниже держит этот порядок.

Терминология DUP/NIL/RST/NR сверена с `Readme.txt` из VE3NEA/MorseRunner:

- **DUP** — повторная связь.
- **NIL** — станции нет в чужом логе: ошибка в позывном или не отправлена
  исправленная копия.
- **RST** — неверный RST в логе.
- **NR** — неверный серийный номер/обмен.
- **Raw** — счёт по своему логу как есть. **Verified** — счёт после сверки
  с логами других станций.

Важный нюанс: в MorseRunner Verified — это сверка *с другой стороной*,
которая тоже может ошибаться (band condition LIDS). У нас пока нет
симуляции ошибок корреспондента, поэтому честный Verified в понимании
MorseRunner потребует смоделировать, что корреспондент "записал" о вас —
это отдельная under-the-hood фича (см. этап 1, пункт про LIDS). Первая
версия даёт Verified как сверку с эталоном движка (без ошибок с их
стороны) — это уже полезно и покрывает 90% ценности.

## Этап 1 — движок верификации

Цель: движок знает точный обмен каждой станции и классифицирует ответ
пользователя кодами DUP/NIL/RST/NR, независимо от режима.

Сейчас часть этого уже есть, но размазана:
- `scoring.js::addQSO()` уже ловит дубль (`DUPE` бейдж) и общую ошибку
  (`hasError` → 0 очков), но не различает *какая* именно ошибка.
- `app.js::compareExtraInfo()` (строки ~924+) сверяет серийник/RST/имя
  внутри `tu()`, но результат не долетает до `scoringSystem` как код
  ошибки — только красит ячейку в таблице.
- Позывной вообще не проверяется на этапе `tu()` — `compareStrings()` в
  `util.js` используется только для управления звуковым потоком в `send()`
  (perfect/partial/none), а не для итоговой классификации NIL.

**Что сделать:**

1. Новый модуль `src/js/verification.js` — чистые функции без DOM и без
   побочных эффектов (следуя правилу CLAUDE.md: "логика, которую можно
   вынести в чистую функцию, должна ехать в тесты, а не в консоль").
   - `classifyQso(mode, groundTruthStation, userLog)` →
     `{ codes: ('NIL'|'RST'|'NR')[], verified: boolean }`.
   - Переносит сюда логику из `compareExtraInfo()` (перенести, не
     дублировать — старую версию в `app.js` удалить).
   - Добавляет проверку позывного (NIL), которой сейчас нет: сверяет
     `userLog.callsign` со station.callsign через ту же логику, что и
     `compareStrings`, но здесь нужен факт "исправлено/не исправлено",
     а не только perfect/partial/none.
2. `scoring.js`:
   - `ScoringSystem` получает `rawScore` (как насчитал бы пользователь,
     если бы не знал об ошибках) отдельно от текущего `points` (де-факто
     уже Verified — считается только по корректным QSO). Переименовать
     `points`/`totalScore` в `verifiedPoints`/`verifiedScore`, добавить
     `rawPoints`/`rawScore`.
   - `addQSO()` принимает `verification.codes` вместо одного `hasError`,
     сохраняет коды в `qso` для лога.
3. `app.js::tu()` — вызывает `classifyQso()`, кладёт коды в объект `qso`
   перед `scoringSystem.addQSO()`, рендерит бейдж по конкретному коду
   (сейчас есть только общий бейдж "не засчитано" и `DUPE`).
4. Scoreboard в `index.html` — колонки Raw / Verified вместо одного счёта.
5. `localization/{ru,en}.js` — ключи для кодов и заголовков колонок.
6. Тесты: `tests/verification.test.mjs` — по кейсу на каждый код плюс
   граничные (пустой ввод, регистр, дробный позывной).

Файлы: `src/js/verification.js` (новый), `src/js/scoring.js`,
`src/js/app.js` (`tu()`, `compareExtraInfo()` — удалить),
`src/index.html`, `src/localization/{ru,en}.js`,
`tests/verification.test.mjs` (новый).

## Этап 2 — строгий режим WPX/HST

Оба режима уже в `modes.js` и `MODE_RULES`, но заблокированы через
`DISABLED_MODES = ['hst', 'wpx']` в `app.js` (строка 289) — конфиги не
удалять, снимать блокировку по готовности каждого отдельно.

### WPX

Формула "очки = QSO × число уникальных префиксов" **уже реализована**:
`getFinalScore()` в `scoring.js` делает `points * multipliers`, а
`MODE_RULES.wpx = { points: 1, multipliers: true, key: 'prefix' }`. Не
трогать эту часть, она верна.

Что реально не готово:

1. **Серийники не идут по порядку.** `stationGenerator.js:436` —
   `serialNumber: Math.floor(Math.random() * 30) + 1` для всех режимов,
   в WPX должно быть последовательно от 001. Решение по образцу уже
   существующего `nonRussianSerialNumber` (тот же файл, строка 352,
   счётчик для RDA): завести `wpxSerialCounter`, инкрементировать при
   каждой генерации станции в WPX-режиме, сбрасывать в
   `resetGameState()` и `reset()` (сейчас там нет сброса даже для
   `nonRussianSerialNumber` — это отдельный баг из CLAUDE.md п.8, чинить
   заодно).
2. **Нет проверки повтора позывного внутри пачки** при генерации —
   сейчас возможна генерация одного и того же позывного дважды в
   `addStations()` (`util.js`). Добавить проверку против
   `scoringSystem.workedCallsigns` при генерации, а не только при логе.
3. **Фиксированные настройки.** Строгий режим не даёт крутить скорость/
   QRN/QSB/длительность. Нужен новый ключ в конфиге режима —
   `logic.strictSettings: { minSpeed, maxSpeed, qrnLevel, qsb, duration }`
   — и в `app.js::applyModeSettings()` при входе в WPX/HST: применить эти
   значения и задизейблить соответствующие контролы в `index.html`
   (сейчас `applyModeSettings()` уже переключает видимость полей по
   `modeConfig.ui`, это тот же паттерн, только на `disabled`).
4. **Очки по диапазону/континенту** — официальные правила CQ WPX
   (cqwpx.com/rules, п. V.B) нашлись: разные континенты — 3 очка на
   28/21/14 МГц и 6 на 7/3.5/1.8 МГц; тот же континент, другая страна —
   1 и 2 очка соответственно (для Северной Америки отдельное исключение:
   2 и 4); та же страна — 1 очко независимо от диапазона. Множитель —
   число уникальных префиксов (это уже верно реализовано).

   Применить как есть — не могу: у тренажёра **нет диапазонов** (один
   аудиоканал, HF-диапазон не выбирается), поэтому "то же значение,
   другой диапазон" не из чего считать. Пробовать натянуть очки по
   континенту на существующую категоризацию станций (`us` / `russian` /
   `international` в `stationGenerator.js`) — нечестно: `international`
   объединяет Европу, Азию, Океанию как один континент, реальные очки
   разъедутся. **Решение: оставить 1 очко/QSO без разбивки** — это
   осознанное упрощение из-за отсутствия диапазонов в архитектуре, а не
   недостаток данных. Если/когда в тренажёр добавится выбор диапазона —
   вернуться к этому пункту, правила уже есть выше.
5. Снять `wpx` из `DISABLED_MODES`, убрать бейдж «СКОРО» для WPX в
   `index.html`/`localization`.

Файлы: `src/js/stationGenerator.js`, `src/js/scoring.js` (если проверка
дублей переедет туда), `src/js/app.js`, `src/js/util.js`, `src/index.html`.

### HST

Нашёл официальный регламент IARU Region 1 (iaru-r1.org/.../hst-rules,
редакция апрель 2024). У чемпионата четыре дисциплины: приём групп букв/
цифр/смешанного текста на нарастающей скорости (ZEUS), передача тех же
групп ключом (HST2006), приём реальных позывных (RUFZ XP) и pile-up тест
(это буквально Morse Runner — регламент прямо ссылается на VE3NEA
Morse Runner v1.67 с зафиксированным конфигом, см. ниже).

Из четырёх дисциплин тренажёру подходят две — под остальные (передача
ключом, абстрактные группы букв/цифр) в Morse Walker нет ни механики
(нет приёма с клавиатуры-ключа), ни концепции самого упражнения (сейчас
всё построено вокруг QSO, не вокруг групп символов). Это отдельная,
более крупная фича, не вписывается в этот этап.

**D2.3.1, приём позывных (аналог RUFZ XP)** — ложится почти один в один
на уже существующий `single`-режим: 50 реальных позывных, скорость
растёт после верно принятого и падает после ошибки, 2 попытки с лимитом
времени на попытку (в регламенте — 13 минут на вход в комнату, не факт,
что это ограничение имеет смысл переносить дословно), засчитывается
лучшая попытка. Конкретный шаг изменения скорости в самом регламенте
чемпионата **не задан** — это поведение софта RUFZ XP, а не правило
IARU; если понадобится в точности повторить RUFZ XP — придётся смотреть
исходники/поведение этой программы отдельно, регламент чемпионата тут
не источник.

**D2.3.2, pile-up тест** — прямо использует Morse Runner с фиксированным
конфигом (Appendix I регламента):

```
Duration=10          // минут на попытку
Activity=4
QRN=0  QRM=0  QSB=0  Flutter=0  Lids=0   // чистый эфир, без помех
Band Width=10
```

Это готовый набор `strictSettings` для нашего pile-up-режима HST —
10 минут, никаких QRN/QSB, 2 попытки, лучшая засчитывается.

**QRM (интерференция от других работающих станций) в Morse Walker вообще
не смоделирован** — ни в обычных режимах, ни, соответственно, тут. Не
блокирует реализацию (по регламенту он всё равно должен быть выключен:
`QRM=0`), но стоит знать на будущее — если решите добавлять QRM в другие
режимы, HST от этого не зависит.

Реализация: новый модуль `src/js/hst.js` (таймер попытки, лучшая из
двух, кривая роста/падения скорости для callsign-теста), `modes.js::hst`
разделяется на два подрежима или получает переключатель
callsign/pile-up, `scoring.js::MODE_RULES.hst` — очки по числу верно
принятых позывных за фиксированное время вместо текущего плоского
`{points: 1}`. Открытый вопрос остался один — точный шаг скорости в
RUFZ-тесте, регламент чемпионата его не определяет.

## Этап 3 — бэкенд

Ключевая проблема уже верно названа в CLAUDE.md: клиент знает правильный
ответ (генерирует его сам), поэтому доверять клиентскому счёту для
официального зачёта нельзя. Это определяет архитектуру: **сервер должен
быть источником истины для сессии**, а не просто складом для
клиентского счёта.

**Рекомендация по стеку: Supabase**, не самодельный Node+Postgres сервер.
Причины: один поддерживающий разработчик (R9OGL), уже есть Postgres "из
коробки", auth (email/magic-link) не пишется руками, Row Level Security
закрывает доступ к чужим сессиям без отдельного слоя авторизации. Чистый
Node-бэкенд оправдан, только если понадобится держать WPM-генерацию или
серьёзную кастомную логику вне SQL/Edge Functions — на первом проходе не
понадобится.

**Модель серверной сессии:**

1. Клиент запрашивает `POST /sessions` (Supabase Edge Function) —
   передаёт режим (`wpx`/`hst`) и настройки, сервер генерирует случайный
   `seed`, создаёт запись сессии, возвращает `session_id` + `seed`.
2. Генерация станций (`stationGenerator.js`) должна стать **детерминированной
   по seed** — сейчас всё на `Math.random()`. Нужно завести общий
   сидируемый ГПСЧ (например, mulberry32, ~10 строк, без зависимостей) и
   прокинуть его вместо прямых вызовов `Math.random()` во всех функциях
   генерации (`getRandomUSCallsign`, `getRandomRussianCallsign`, серийники,
   выбор QSB и т.д.). Это самое инвазивное изменение файла — сейчас там
   `Math.random()` разбросан по ~15 местам.
3. Тот же сидируемый генератор запускается **и в браузере (для звука и
   пайлапа), и на сервере (Edge Function, тот же алгоритм на TS/JS)** —
   раз оба используют одинаковый seed и одинаковый ГПСЧ, оба посчитают
   одну и ту же последовательность станций независимо. Сервер не
   стримит станции клиенту — экономит трафик и не палит ответы заранее.
4. Игра идёт локально как сейчас. По окончании сессии клиент отправляет
   `POST /sessions/:id/submit` с логом QSO (что ввёл пользователь по
   каждой станции, по порядку). Сервер по seed пересчитывает ту же
   последовательность станций, гоняет `classifyQso()` (та же чистая
   функция из этапа 1, но теперь и на сервере — хороший повод сразу
   писать её без DOM-зависимостей) и сам считает Raw/Verified счёт.
   Клиентский счёт в БД не пишется вообще — только пересчитанный.
5. Античит этим не закрывается полностью (можно вручную набрать
   идеальный лог, не играя), но убирает главную дыру — модификацию счёта
   через консоль/DevTools, потому что счёт не приходит от клиента.

**Идентификация по позывному** — как и отмечено в CLAUDE.md, это отдельная
проблема, решать после MVP лидерборда: первая версия может публиковать
результаты без верификации владения позывным (как "неофициальный" зачёт),
пометка "подтверждён" — когда появится привязка к email из QRZ или ручная
модерация.

### Схема БД (Postgres/Supabase)

```sql
create table profiles (
  id            uuid primary key references auth.users(id),
  callsign      text not null,
  callsign_verified_at timestamptz,
  created_at    timestamptz not null default now()
);
create unique index on profiles (lower(callsign));

create table sessions (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references profiles(id),
  mode          text not null check (mode in ('wpx', 'hst')),
  seed          bigint not null,
  settings      jsonb not null,        -- зафиксированные strictSettings на момент старта
  status        text not null default 'in_progress'
                  check (status in ('in_progress','submitted','abandoned')),
  started_at    timestamptz not null default now(),
  finished_at   timestamptz,
  duration_s    integer not null,
  client_version text
);

-- эталон движка на сервере, генерируется по seed при сабмите,
-- хранится для разбора споров и повторной проверки
create table session_stations (
  id            bigserial primary key,
  session_id    uuid not null references sessions(id) on delete cascade,
  seq_no        integer not null,
  callsign      text not null,
  exchange      jsonb not null,        -- { rst, serial } | { rst, region } и т.д.
  wpm           integer not null,
  unique (session_id, seq_no)
);

create table qso_log (
  id              bigserial primary key,
  session_id      uuid not null references sessions(id) on delete cascade,
  station_id      bigint not null references session_stations(id),
  submitted_callsign text,
  submitted_exchange jsonb,
  codes           text[] not null default '{}',   -- DUP/NIL/RST/NR, пусто = OK
  raw_points      integer not null default 0,
  verified_points integer not null default 0,
  is_new_multiplier boolean not null default false,
  unique (session_id, station_id)
);

create table leaderboard_scores (
  session_id      uuid primary key references sessions(id),
  user_id         uuid not null references profiles(id),
  mode            text not null,
  qso_count       integer not null,
  multiplier_count integer not null,
  raw_score       integer not null,
  verified_score  integer not null,
  accuracy        numeric(5,2) not null,
  submitted_at    timestamptz not null default now(),
  is_public       boolean not null default true
);

create index on leaderboard_scores (mode, verified_score desc);
create index on sessions (user_id, mode);
```

`leaderboard_scores` — денормализованная таблица, которую заполняет
Edge Function при `submit`, а не view: лидерборд читается часто и должен
быть дешёвым запросом без пересчёта агрегатов на лету.

RLS: `sessions`/`qso_log`/`session_stations` — доступ только
`user_id = auth.uid()`; `leaderboard_scores` — публичное чтение при
`is_public = true`, запись только через Edge Function (service role), не
напрямую от клиента — иначе античит на шаге 4 бессмысленен.

## Этап 4 — лидерборд на фронте

1. Новый модуль `src/js/leaderboard.js` — `fetchLeaderboard(mode)` через
   Supabase JS client, рендер таблицы (переиспользовать паттерн
   `addTableRow()` из `util.js` или отдельная лёгкая функция — там нет
   построчной сверки, только вывод).
2. Точка входа в UI: пункт в навигации/модалка, по аналогии с существующими
   модалками помощи в `index.html`. Referencing dxatlas MrScore.asp — как
   у них, отдельная страница/секция, не встроено в основной экран тренажёра.
3. После завершения строгой сессии (таймер WPX/HST истёк) —
   `app.js` вызывает submit из этапа 3, показывает результат и ссылку
   "посмотреть в лидерборде".
4. `localization/{ru,en}.js` — тексты лидерборда, статусов сессии.
5. Фильтры: по режиму (wpx/hst) обязательно, по периоду — опционально,
   можно отложить.

Файлы: `src/js/leaderboard.js` (новый), `src/js/app.js`, `src/index.html`,
`src/localization/{ru,en}.js`.

## Порядок и зависимости

```
Этап 1 (верификация, чистые функции + тесты)
   │  classifyQso() переиспользуется этапом 3 на сервере
   ▼
Этап 2 (строгий WPX сразу; HST — блокирован регламентом от R8OA)
   │  strictSettings и WPX serial counter нужны для честной серверной сессии
   ▼
Этап 3 (бэкенд, Supabase, сидируемый ГПСЧ, серверная сверка)
   ▼
Этап 4 (лидерборд на фронте)
```

Этапы 1–2 не требуют бэкенда и дают пользу сами по себе (честная сверка
обмена, рабочий WPX) — можно катить в прод независимо от того, когда
дойдут руки до этапа 3. Этап 3 — самый рискованный по объёму (сидируемый
генератор, Edge Functions, RLS) и по времени лучше закладывать отдельным
циклом, не смешивая с 1–2 в одном PR.
